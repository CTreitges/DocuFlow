## 2. Code-Audit (priorisiert)

**HIGH** (s. K1, K2 oben)

**MEDIUM**
- **Deutsche Tausender falsch geparst:** `'1.234'` → `1.234` statt `1234.0`, `'1.500'` → `1.5`. Betrifft OCR- (`ocr_engine.py:435`) **und** Template-Pfad (`template_matcher.py:100`). → `auto-optimize` hat den Fix (`number_parser.parse_amount`), wird auf diesem Branch aber nicht genutzt.
- **`aiosqlite` versprochen, sync `sqlite3` implementiert** — Single-Connection, `check_same_thread=True`. Heute kein Race (alle DB-Zugriffe auf Loop-Thread), aber scharfer Cross-Thread-Footgun + blockierendes I/O auf dem Event-Loop. (`database.py:25`)
- **OCR-Singleton ohne Lock** — Doppel-Laden des Modells → doppelter VRAM auf der 1080 Ti möglich. (`ocr_engine.py:53-62`)
- **Watchdog nur `on_created`** — verpasst Rename/Move (Scanner/Downloader schreiben `.tmp`→`.pdf`), liest evtl. truncierte PDFs (keine Größen-Stabilitätsprüfung). (`watchdog_service.py:18-25`)
- **`open()` ohne `encoding`** beim YAML-/Config-Lesen → Mojibake/Crash bei Umlauten auf Windows (cp1252). → `auto-optimize` fixt das (UTF-8). (`config.py:25`, `template_matcher.py:25`, `rules_store.py:23`)

**LOW**
- TOCTOU-Race + nicht-atomarer Move in `move_file`/`undo_sort`.
- `asyncio.get_event_loop()` deprecated unter Python 3.13/3.14 (`ocr_engine.py:86,124`).
- `raw_text` wird redundant in jede DB-Zeile serialisiert (DB-Bloat bei mehrseitigen PDFs).
- Config-Cache greift nach Processor-Konstruktion nicht → Settings-Änderungen (Auto-Modus/Threshold) wirken erst nach Neustart.

> Bewusst **kein** Bug: `get_history_filtered` ist **keine** SQL-Injection (der f-string injiziert nur fixe Literale, nie den Wert). Kein aktiver Thread-Race (Watchdog macht nur `queue.put`).

## 3. OCR-Realität & Performance-Wahrheit

- **`german-ocr` real:** PyPI v0.6.0, `pip install german-ocr[llamacpp]` (CPU) bzw. mit `CMAKE_ARGS="-DGGML_CUDA=on"` für CUDA. Aber bei `backend='ollama'` ist es **kein** eigener Runtime, nur ein eigenes Modell über denselben Ollama-Server.
- **Heute nichts lauffähig:** Ollama-Daemon down (`connection refused`), `ollama`/`german-ocr` in keinem Interpreter, kein `venv`. Python-Drift: PATH-Python ist 3.14.4, CLAUDE.md sagt 3.13.
- **Performance-Wahrheit (wichtig für die Frontend-Frage):**
  - Ein Frontend-Swap macht **nur die UI-Latenz** besser — NiceGUI macht pro Klick einen Websocket-Roundtrip; Navigation/Regel-Editor/Inbox fühlen sich danach spürbar snappier an. ✅ real.
  - Er bringt **nichts** für die Dokumentenverarbeitung — die ist GPU/Ollama-Inferenz-gebunden. Eine 8s-OCR bleibt 8s. ❌
  - Der echte Verarbeitungs-Hebel: **Modellwahl** (`glm-ocr` 0.9B statt `minicpm-v` 8B — auf der Pascal-GPU der größte Gewinn), DPI (aktuell 200), nur Seite 1 wird ge-OCR-t (Kosten gedeckelt).
  - → **Zwei getrennte Baustellen:** Frontend = gefühlte Reaktivität · Verarbeitung = Modell/DPI/GPU. Nicht verwechseln.

## 5. Frontend-Stack — Empfehlung

**Harte Constraints:** Backend bleibt Python und lokal (Ollama+GPU, watchdog-Ordnerüberwachung, lokale Datei-Verschiebung, SQLite, PyMuPDF). Die load-bearing Frage ist **Desktop-Shell vs. lokal-served Browser-App** — *nicht* Svelte-vs-React. Auf Windows rendern beide über dieselbe Engine (EdgeWebView2); der Unterschied ist Verpackung/Lifecycle, nicht Render-Performance.

**Empfehlung: (d) pywebview + FastAPI + Svelte 5 (Vite-SPA) als Desktop-Shell.**
- Maximiert alle drei Prioritäten: **Optik** (freies Svelte+Tailwind statt Quasar-Deckel), **Performance** (Client-State-SPA, niedrigste Interaktions-Latenz), **Flexibilität** (beliebige Komponenten + freie API über das bestehende `core/`).
- Liefert echte Fenster-Shell mit sauberem Lifecycle (Fenster zu = watchdog + Ollama stoppen) **ohne** Rust/Sidecar-Overhead.
- Deckungsgleich mit dem Schwesterprojekt-Plan **CTR-6** (Lieferschein-Processor: FastAPI+Svelte+pywebview+PyInstaller).
- Wichtig: **kein SvelteKit-SSR**, sondern reines Vite-Svelte-SPA (`adapter-static`). Der API-Layer hält den späteren Wechsel zu Tauri offen.

**Runner-up: (c) Tauri 2 + SvelteKit + Python-FastAPI-Sidecar** — gleiche Optik/Performance plus produktreife Distribution (Auto-Updater, signierte Installer, Tray). Heute overengineered für ein reines Localhost-Tool (drei Toolchains, Sidecar-Lifecycle fragil), aber Ziel-Stack sobald DocuFlow ein verteilbares Produkt mit Auto-Update werden soll. Der Sprung (d)→(c) ist später billig, da Frontend + Backend geteilt.

| Option | Optik | UI-Perf | Flexibilität | Aufwand | Fit |
|--------|:--:|:--:|:--:|:--:|-----|
| (a) NiceGUI + Redesign | Mittel | Gut | Mittel | sehr niedrig | Fallback, an Quasar gedeckelt |
| (b) FastAPI + Svelte5 **Browser** | sehr hoch | sehr gut | sehr hoch | hoch | gut, aber Browser passt schlechter zum Dauer-Tool |
| **(d) pywebview + FastAPI + Svelte5** | **sehr hoch** | **sehr gut** | **sehr hoch** | hoch | **bester Gesamt-Fit** |
| (c) Tauri2 + Sidecar | sehr hoch | sehr gut | sehr hoch +OS | sehr hoch | top, aber heute overengineered |
| (e) Electron + React | hoch | gut, schwer | sehr hoch | hoch | schlechtester Fit (Footprint, gegen Svelte) |

# DocuFlow Frontend-Stack-Vergleich

## Load-bearing Entscheidung: Desktop-Shell vs lokal-served Browser-App

Beide Varianten teilen dasselbe Backend (FastAPI/uvicorn auf 127.0.0.1) und auf Windows
dieselbe Render-Engine EdgeWebView2 (Chromium) - egal ob pywebview-Shell oder Browser-Tab.
Der Unterschied ist NICHT Performance (Loopback ca. 1ms, gerendertes Frontend byte-identisch),
sondern Verpackung/UX.

- Desktop-Shell (pywebview/Tauri): eigenes Fenster, App-Icon, kein Adressbalken, sauberes
  window-close-Event zum Stoppen der Hintergrund-Services (watchdog, Ollama-Subprozess),
  natives Produkt-Gefuehl. Preis: Shell-Lifecycle + Packaging (PyInstaller, ggf. Rust).
- Browser-App (FastAPI serviert SPA, im Browser): null Shell-Code, kein Packaging, voller
  DevTools-Zugriff, PWA-faehig. Preis: Browser-Chrome drumherum, Service-Lifecycle nicht ans
  Fenster gekoppelt (Tray noetig), weniger Produkt-Gefuehl.

FAZIT: DocuFlow ist ein dauerlaufendes, datei-/systemnahes Hintergrund-Tool
(Ordnerueberwachung, Datei-Verschiebung, lokaler GPU-Dienst). Die Desktop-Shell gewinnt klar
wegen Lifecycle-Kopplung (Fenster zu = Services stoppen) und Produkt-Optik. pywebview ist die
richtige Stufe (leicht, Python-nativ, dasselbe WebView2). Tauri ist die schwerere Stufe, nur
gerechtfertigt wenn echte OS-Integration (Auto-Updater, signierte Installer, Tray, tiefe
FS-/Notification-APIs) zum Top-Ziel wird.

## Empfehlung: (d) pywebview + FastAPI + Svelte 5 (Vite-SPA) als Desktop-Shell

Maximiert die drei vom User priorisierten Achsen - Optik (freies Svelte+Tailwind statt
Quasar-Deckel), Performance (Client-State-SPA, niedrigste Interaktions-Latenz, WebView2-Render
identisch zu Tauri) und Flexibilitaet (beliebige Komponenten + freie API ueber bestehendes
Python-core/) - und liefert zugleich die echte Fenster-Shell mit sauberem Lifecycle
(Fenster-Close stoppt watchdog + Ollama) ohne Rust+Sidecar-Overhead. Deckungsgleich mit
Schwesterprojekt CTR-6 (FastAPI+Svelte+pywebview+PyInstaller). Wichtig: KEIN SvelteKit-SSR,
sondern reines Vite-Svelte-SPA mit adapter-static (SPA-Mode bei lokalem Server optimal, SSR
fuer Localhost-Tool kontraproduktiv). Der API-Layer ermoeglicht spaeteren Wechsel zu Tauri (c)
ohne Aenderung an Frontend/Backend.

## Runner-up: (c) Tauri 2 + SvelteKit + Python-FastAPI-Sidecar

Gleiche erstklassige Optik/Performance/Flexibilitaet wie (d) plus produktreife Distribution
(Auto-Updater, signierte Installer, Tray, tiefe OS-APIs). Heute overengineered fuer reines
Localhost-Tool (Rust-Toolchain + PyInstaller-Sidecar + manuelles Sidecar-Lifecycle, kein
Render-Vorteil ggue. pywebview wegen gleichem WebView2), aber Ziel-Stack sobald DocuFlow
verteilbares Produkt mit Auto-Update wird. Sprung (d)->(c) spaeter billig, da Frontend+Backend
geteilt.

## Optionen im Detail

### (a) NiceGUI behalten + Redesign [desktop-shell]
- Stack: NiceGUI (Vue+Quasar+Tailwind, FastAPI intern) + pywebview native.
- Pro: Null Migration (~3700 LOC bleiben); UI+Backend in einem Prozess, kein API-Layer;
  Tailwind bereits da (design.py); native nutzt dasselbe WebView2.
- Contra: Optik durch Quasar gedeckelt (angestaubt); Roundtrip pro Interaktion (server-side
  State) -> traeger bei 40-Widget-Regel-Editor/Filter/Drag-and-Drop; Custom-Komponenten fragil
  (.props bricht ausserhalb Quasar); inkonsistent mit CTR-6.
- Optik: Mittel | Performance: Gut, aber server-side State weniger snappy | Flexibilitaet:
  Mittel (an Quasar gebunden) | Aufwand: Sehr niedrig.
- Fit: Hoch fuer Time-to-Value, mittel fuer die Ziele. Limitiert genau bei Optik+Flexibilitaet.
  Fallback, kein Ziel-Stack.

### (b) FastAPI + Svelte 5 (Vite-SPA) als Browser-App [local-browser-app]
- Stack: FastAPI (core/ als API) + Svelte 5 + Vite + adapter-static (kein SSR) + Tailwind, im Browser.
- Pro: Volle Design-Freiheit; Client-State -> snappy, Python nur bei echtem I/O, beste Latenz;
  Svelte 5 klein, kein Virtual DOM; null Shell/Packaging, API spaeter headless/REST.
- Contra: Browser-Chrome, weniger Produkt-Gefuehl; Lifecycle (watchdog/Ollama) nicht ans Fenster
  gekoppelt (Tray noetig); voller UI-Rewrite + API; zwei Toolchains.
- Optik: Sehr hoch | Performance: Sehr gut (niedrigste Latenz) | Flexibilitaet: Sehr hoch |
  Aufwand: Hoch (ohne Shell/Packaging).
- Fit: Sehr gut auf Optik/Performance/Flexibilitaet, aber Browser-Verpackung passt schlechter zum
  Dauer-Tool. Faktisch das halbe Ziel von (d).

### (c) Tauri 2 + SvelteKit + Python-Sidecar [hybrid]
- Stack: Tauri 2 + Svelte/SvelteKit-static + Tailwind; FastAPI als Sidecar (PyInstaller, externalBin).
- Pro: Native Shell (Auto-Updater, signierte Installer, Tray, OS-APIs, PLAN Phase 4); gleiche
  Svelte-Optik/Performance wie (b)/(d); Christof kennt Tauri+Svelte (ImpForge); sauberste Distribution.
- Contra: Drei Build-Welten (Rust+npm+Python); Sidecar-Bundling (PyMuPDF/ollama/german-ocr/GPU)
  fehleranfaellig, TARGET_TRIPLE-Pflicht; Sidecar-Lifecycle manuell killen (sonst Zombie-uvicorn) +
  Ollama; WebView2 wie pywebview -> kein Render-Vorteil ggue. (d); widerspricht CTR-6.
- Optik: Sehr hoch | Performance: Sehr gut (wie pywebview) | Flexibilitaet: Sehr hoch + OS-Integration
  | Aufwand: Sehr hoch.
- Fit: Optik/Performance top, aber heute overengineered. Richtig erst bei Installer/Auto-Update-Bedarf.

### (d) pywebview + FastAPI + Svelte 5 (Vite-SPA) Desktop-Shell [desktop-shell] -- EMPFEHLUNG
- Stack: pywebview (WebView2) + FastAPI (core/ als API) + Svelte 5 Vite-SPA (adapter-static) +
  Tailwind; PyInstaller. = CTR-6-Stack.
- Pro: Optik/Performance/Flexibilitaet von (b) PLUS echte Fenster-Shell; Lifecycle gekoppelt
  (Close stoppt watchdog+Ollama); reiner Python-Wrapper, kein Rust, leichter als Tauri; dasselbe
  WebView2 wie Tauri; konsistent mit CTR-6; ein Python-Bundle (kein TARGET_TRIPLE); Upgrade-Pfad
  zu (c) offen.
- Contra: Voller UI-Rewrite + API; zwei Toolchains; Shell duenner als Tauri (kein Auto-Updater/Tray
  out-of-the-box); PyInstaller-GPU/OCR-Bundling in sauberer Umgebung testen.
- Optik: Sehr hoch | Performance: Sehr gut (Client-SPA, WebView2 wie Tauri) | Flexibilitaet: Sehr
  hoch im Frontend | Aufwand: Hoch, aber deutlich unter (c).
- Fit: Bester Gesamt-Fit. Maximiert die drei Prioritaeten + Fenster/Lifecycle-Shell ohne
  Rust+Sidecar, deckungsgleich mit CTR-6.

### (e) Electron + React [desktop-shell]
- Stack: Electron (Chromium+Node) + React; FastAPI als separater Prozess.
- Pro: Reifstes Ecosystem; konsistente Chromium-Engine; groesster React-Pool.
- Contra: Schwerster Footprint (~150-300MB RAM, ~80-150MB Installer vs ~10-50MB); buendelt Chromium
  trotz lokalem WebView2 (Verschwendung); Python dritter Prozess neben Node; gegen den Svelte-Skill
  (ImpForge/CTR-6); kein Vorteil der die Kosten rechtfertigt.
- Optik: Hoch (nicht besser als Svelte) | Performance: Render gut, schwerster Overhead | Flexibilitaet:
  Sehr hoch (aber Node+Python) | Aufwand: Hoch.
- Fit: Schlechtester Fit. Max Overhead ohne Gegenwert, gegen den Svelte-Skill.
